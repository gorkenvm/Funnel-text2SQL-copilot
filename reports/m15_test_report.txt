M15 — Demo gate: "Build top-12" regression report + 401 hardening
====================================================================

Bug report
----------
"With the M13 demo gate ENABLED (just turned it on and unlocked
successfully), 'Build top-12 KPI dashboard' does nothing and 'Reset
layout' appears broken too. With the gate off everything worked."
Hypothesis given: some frontend call sites bypass demoGateHeaders(), so a
gated call gets a silent 401 and renders nothing (an empty grid then makes
Reset layout look dead as a side effect, per the M14-fix report).

Investigation
-------------
Static audit of every network call site in app/static/index.html BEFORE
any change, cross-checked against app.main._demo_gate_middleware:

  Call site                              | Path            | Header before  | Gated?
  ----------------------------------------|-----------------|----------------|--------
  apiPost() (used by buildDashboard,     | /api/dashboard, | demoGateHeaders| yes
    sendQuestion's POST fallback)        | /api/ask        | (X-Demo-Key)   |
  apiGet() (used by pollHealth,          | /health,        | demoGateHeaders| /health:
    checkDemoGate, openCatalogPanel)     | /api/catalog    | (X-Demo-Key)   | no (open)
                                          |                 |                | /api/catalog: yes
  validateStoredDemoKey() raw fetch      | /api/metrics    | demoGateHeaders| yes
    (bootstrap: is a stored key still    |                 | (X-Demo-Key)   |
    valid?)                              |                 |                |
  demo-lock-form submit raw fetch        | /api/metrics    | X-Demo-Key:    | yes, but
    (testing a CANDIDATE passphrase,     |                 | <candidate>    | intentionally
    intentionally not yet in demoKey)    |                 | (not stored)   | not via
                                          |                 |                | demoGateHeaders
  streamAsk()'s EventSource              | /api/ask/stream | `&k=` query    | yes (the one
    (cannot set headers)                 |                 | param          | endpoint that
                                          |                 |                | accepts `k`)
  downloadCsv()                          | (none — client- | n/a            | n/a, never
                                          | side Blob only) |                | hits the API

Every current call site already attached the header (or, for the two
demo-lock-flow fetches, correctly did NOT — they predate having a trusted
key at all). Live reproduction (Playwright: restart on port 8130 with
DEMO_PASSPHRASE="open sesame demo", fresh load, unlock via the lock
screen, click "Build top-12 KPI dashboard", capture every /api/* request's
headers and response status) confirmed this — BEFORE any code change:

    GET  /api/metrics    X-Demo-Key: open sesame demo   200
    POST /api/dashboard  X-Demo-Key: open sesame demo   200
    -> 12 cards rendered, 0 console/page errors.

The exact reported symptom ("Build top-12 does nothing") did NOT
reproduce with the current code, tried multiple ways: fresh unlock, and
unlock-then-reload-then-build (sessionStorage persistence). So this is
NOT a "some call site is missing the header today" bug in the current
file — every current path is fine.

What WAS a real, confirmed gap
-------------------------------
Neither apiGet() nor apiPost() (nor validateStoredDemoKey(), before this
fix) did anything special with a 401. A 401 only ever meant "this
particular request failed" to the caller — buildDashboard()'s `.catch`
shows a generic toast, and nothing re-displays the lock screen or clears
the now-known-bad stored key. So the ACTUAL failure mode this hardens
against is a stale key mid-session (the operator rotates
DEMO_PASSPHRASE, or a session simply outlives the currently-configured
one) while the tab stays open: every subsequent gated call would keep
silently failing with a generic error toast, the user would see cards
never renders / actions "doing nothing", and have no clue why or what to
do about it — which matches the reported symptom's shape even though the
originally-suspected cause (a missing header on some call site) was not
actually present. This is exactly the class of "silent failure" the
coordinator's message called out, and is worth fixing regardless of the
exact trigger, since a 401 can appear on ANY gated call at ANY time (key
rotation, expired demo, etc.), not only immediately after unlocking.

Confirmed via a route-interception test (page.route intercepting
/api/dashboard to return the exact 401 body app.main._demo_gate_middleware
sends for a bad key) — see "Validation" below.

Fix
---
app/static/index.html, M15 section, around demoGateHeaders()/apiPost()/
apiGet():

1. New `demoGateQueryParam()` — factors out the EventSource `&k=...`
   logic (previously an inline `if (demoKey) url += "&k=" + ...` in
   streamAsk()) so a future second EventSource call site can't forget it.

2. New `handleDemoGateExpiry(status, json)` — on a real 401 (not 429,
   which is a temporary per-IP lockout unrelated to whether THIS key is
   valid), clears the in-memory `demoKey` and its sessionStorage entry,
   re-shows the lock overlay, and sets its error text from the server's
   message (falling back to the existing "wrong passphrase" i18n string).
   429 is deliberately left alone — re-locking someone whose key is fine
   just because of a transient rate-limit would be wrong.

3. New `apiFetch(path, options)` — the ONE place a response's `!resp.ok`
   is turned into both (a) `handleDemoGateExpiry()` and (b) the thrown
   Error every existing caller already expects (same shape as before:
   `err.status`, `err.payload`). `apiPost()` and `apiGet()` are now thin
   wrappers over `apiFetch()`, so every existing call site (dashboard
   build, ask, catalog, metrics, health) gets 401-recovery for free with
   no call-site changes, and any FUTURE endpoint added via apiGet/apiPost
   automatically inherits both the header and the 401 handling — it is no
   longer possible to add a new gated call that forgets either.

4. `validateStoredDemoKey()` (the boot-time "is my stored key still
   good?" check) simplified to call `apiGet("/api/metrics")` instead of
   its own raw fetch + duplicate clear-and-relock logic — that logic now
   lives once, in `handleDemoGateExpiry()`.

The demo-lock-form's own candidate-testing fetch (line ~2589, testing a
just-typed passphrase that ISN'T the trusted `demoKey` yet) is
deliberately left as its own raw fetch: it must send the CANDIDATE value,
not `demoGateHeaders()`'s stored one, and its 401/429 branches already
show distinct, purpose-built messages ("wrong passphrase" vs "too many
attempts, wait") — routing it through the generic 401 handler would only
duplicate/confuse that existing, correct logic.

M16 — "Clear dashboard" semantics + shortened catalog comments
==================================================================

1) Reset layout -> Clear dashboard (semantics change)
-------------------------------------------------------
User's explicit expectation: clicking the link must clear the ENTIRE
dashboard back to the empty state — every card (board-built AND ad-hoc
chat cards), all chart instances disposed, board-state localStorage
cleared, the M11 filter chip cleared, and the empty-state placeholder
shown. The previous (M14-fix) behavior only reset order/closed/chartType
and redrew the same board cards, or — when no board had ever been built —
cleared just the ad-hoc cards; a user who built the top-12 board, added an
ad-hoc chart, then clicked it, saw only the ad-hoc card disappear and the
12 board cards stay, which they correctly reported as still broken
relative to what they now say the button should do.

Fix (app/static/index.html):
  - `resetBoardLayout()` renamed to `clearDashboard()` and rewritten to
    unconditionally: reset `boardState` to defaults + persist it, set
    `lastDashboardCards = null` (so a stale board can never reappear
    behind the now-empty grid), dispose every live chart instance, empty
    `#grid`, call `hideDashFilterChip()`, and show the empty-state
    placeholder. No more branching on whether a board was ever built —
    every path now ends at the same fully-empty state.
  - i18n: the label itself renamed for honesty, since "Reset layout" no
    longer describes what the button does. `resetLayoutLink` ->
    `clearDashboardLink`: EN "Reset layout" -> "Clear dashboard", TR
    "Yerleşimi sıfırla" -> "Panoyu temizle". The button's DOM id
    (`reset-layout-btn`) and CSS class were left as-is (internal, not
    user-facing) to minimize blast radius.
  - Splitter width, theme, and language are untouched, exactly as
    specified — this function never touched them before and still
    doesn't.

2) Catalog drawer: first-sentence comments + "More"/"Daha fazla" toggle
--------------------------------------------------------------------------
The medallion COMMENT ON texts (medallion.sql) are multi-sentence,
written for the agent and Databricks' own metadata — left completely
untouched, per the coordinator's instruction. Only the catalog DRAWER's
rendering changed: each item now shows just its first sentence, muted
(--ink-muted, unchanged), followed by an inline "More" toggle in --accent
that expands the full comment in place; clicking it again collapses back
to "Less" -> the short form.

Fix (app/static/index.html):
  - `splitFirstSentence(text)` — splits on the first ". " that looks like
    a real sentence boundary (period+space followed by a capital letter or
    "("), trivially robust against abbreviations like "e.g." (typically
    followed by a lowercase word, so the lookahead doesn't match there).
    Returns `{first, rest}`; `rest` is "" when the whole comment is
    already one sentence — verified against the real /api/catalog payload
    (e.g. "...one row per event. Grain: event. Caveat: ..." splits exactly
    after "one row per event.").
  - `buildCatalogCommentHtml(commentText)` — single-sentence comments
    render unchanged (no toggle, nothing to expand); multi-sentence ones
    render the short form plus a `.catalog-comment-toggle` span (styled
    --accent, underlined) carrying the full text as a `data-full`
    attribute on a paired `.catalog-comment-text` span.
  - Wiring: each toggle's click handler calls `e.stopPropagation()` before
    swapping text/label — required because `.catalog-item` (the whole card)
    is itself a clickable `<button>` that inserts the table name into the
    chat input; without stopping propagation, clicking "More" would also
    insert the name. Confirmed via the chat input's value staying empty
    after a toggle click in validation.
  - New i18n keys `catalogCommentMore`/`catalogCommentLess`: EN "More"/
    "Less", TR "Daha fazla"/"Daha az".
  - No backend/`/api/catalog` change was needed — the payload shape was
    already exactly `{name, comment}` per table; the split is purely a
    display-layer concern.

M17 — Richer, engineer-voiced trace step labels
==================================================

User request: the live agent trace should narrate like an engineer at
work ("Writing SQL", "Executing SQL") rather than generic labels
("Planning" / "Fetching metric: ..." / "Writing answer"). Relabel every
SSE-mapped trace step (EN + TR) and, where the architecture already
distinguishes a step's start from its completion, flip the label from a
pending to a done form.

Label changes (app/static/index.html, i18n dicts, EN -> TR):
  event                    | old label            | new label
  -------------------------|-----------------------|---------------------------------------------
  plan                     | Planning              | Planning the approach / Yaklaşım planlanıyor
  tool_call get_schema     | Reading schema        | Inspecting the schema / Şema inceleniyor
  tool_call search_knowledge| Searching knowledge  | Searching the knowledge base / Bilgi tabanında
                            |                       | aranıyor (TR text already matched; EN updated)
  tool_call get_metric     | Fetching metric: <key>| Running governed KPI: <key> / Onaylı KPI
                            |                       | çalıştırılıyor: <key>
  tool_call+sql run_sql    | Running SQL (never    | PENDING "Writing SQL"/"SQL yazılıyor" ->
                            | flipped)              | DONE "Executed SQL"/"SQL çalıştırıldı" on its
                            |                       | tool_result (new: see below)
  retry                    | Fixing query          | Fixing the SQL and retrying / SQL düzeltilip
                            |                       | yeniden deneniyor
  tool_call build_dashboard| Building dashboard    | PENDING "Building the dashboard"/"Dashboard
    (agentic path)         |  (never flipped)      | kuruluyor" -> DONE "Dashboard built"/"Dashboard
                            |                       | kuruldu" on its tool_result (new)
  dashboard event           | Building dashboard   | rendered directly as the DONE label
    (keyless/deterministic |  (never flipped;      | ("Dashboard built"/"Dashboard kuruldu") since
    path, no call_id)      |  misleading — by the  | this event only fires once the dashboard is
                            |  time it appeared the | already fully built — there is no real pending
                            |  dashboard was done)  | phase on this path to show
  context                  | Using context from    | Recalling context / Bağlam hatırlanıyor
                            | previous question     |
  answer                   | Writing answer        | Writing the answer / Cevap yazılıyor (no flip:
                            |                       | this step is only ever added once the answer
                            |                       | has already arrived — 120ms before the trace
                            |                       | collapses into the final bubble — so there is
                            |                       | no genuine pending phase to flip from; kept as
                            |                       | a single label per the coordinator's own
                            |                       | "don't restructure" allowance)

Mechanism for the two new pending->done flips (run_sql, build_dashboard):
  - `addStep(opts)` gained an optional `opts.doneLabel`, stashed as
    `step.dataset.doneLabel` on the rendered element — costs nothing for
    every other step, which simply never sets it.
  - `markDone(callId, secs)` (already called on every "tool_result" event)
    now also checks for that stashed `doneLabel` and, when present,
    overwrites the step's `.trace-label` text — in addition to its
    existing job (adding the "done" class + the secs badge, both
    unchanged).
  - build_dashboard's existing tool_call handler just gained
    `doneLabel: t("traceLabelDashboardDone")` — it already had a
    `callId`, so `markDone()` finds and flips it automatically.
  - run_sql needed one small wiring change: its step has always been
    rendered by the separate "sql" event (which carries the SQL text) —
    but that event never carried a `call_id` of its own to key off. Now
    the preceding "tool_call" event (name === "run_sql") stashes its
    `call_id` on the trace object (`trace.pendingSqlCallId`); the very
    next "sql" event consumes it as that step's `callId` (+ its
    `doneLabel`) and clears the stash. A failed/retried attempt's step
    (whose tool_call never resolves to a matching tool_result) correctly
    stays on "Writing SQL" forever, exactly reflecting that it never
    completed — verified in the synthetic-retry validation below, where
    the FIRST "Writing SQL" step stays unflipped while the SECOND (retried)
    attempt's step flips to "Executed SQL".
  - Icons, secs badges, the retry badge, the SQL disclosure toggle, and
    the collapse/expand behavior are all completely untouched — only
    label strings and this one flip mechanism changed.
