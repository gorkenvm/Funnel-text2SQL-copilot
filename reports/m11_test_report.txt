GOLD CUBES — SCHEMA AND PARITY
-------------------------------
gold.web_funnel_weekly_cube
  Grain:   week_start x market x device_category x channel
  Source:  silver.web_user_stages
  Measures: test_starts, test_completes, store_redirects
  Unfiltered SUM parity (verified by direct DuckDB query and by
  tests/test_dashboard_cubes.py):
    test_starts=100000, test_completes=42062, store_redirects=23405
  — matches gold.funnel_overview / gold.linkable_share_by_market exactly.

gold.journey_weekly_cube
  Grain:   week_start x acquisition_channel x market x platform
  Source:  silver.linked_journeys
  Measures: downloads, paired_users, d30_retained, and (deliberate
  addition beyond the literal 3-measure spec) d30_eligible — the
  right-censoring-aware denominator. d30_retained alone cannot produce
  a correct D30 rate: the raw downloads count would incorrectly include
  cohorts too close to the data horizon to have completed their
  28-34-day observation window (see docs/knowledge/methodology.md's
  pre-existing D30 section, whose logic this cube inherits verbatim).
  Unfiltered SUM parity:
    downloads=6863            (matches gold.downloads_by_channel)
    paired_users=4305         (matches gold.pairing_by_channel)
    d30_eligible=4243 / d30_retained=2204
                               (matches gold.d30_by_channel EXACTLY)

  Note on that last exact match: gold.d30_by_channel's population is
  app_user_stages joined to v_attribution_eligible, which is structurally
  WIDER than silver.linked_journeys (linked_journeys additionally
  requires the temporal-order rule: first app_open strictly after
  hearing_test_complete). On THIS synthetic dataset the two populations
  happen to be identical (6863 rows either way), so the cube's totals
  match exactly rather than merely being a subset. Documented in the
  cube's COMMENT ON and in the test docstrings as a dataset property,
  not a structural guarantee — a future dataset where the temporal-order
  rule actually excludes rows would make the cube a subset of the mart,
  still parity-safe in direction but no longer bit-identical.

Both cubes are added to agent.medallion.GOLD_TABLES (12 -> 14 gold
objects) so they appear in GET /api/catalog and pass the sqlglot
table-allowlist guardrail for ad hoc run_sql use.

FILTERABLE KPI REGISTRY
------------------------
config/dashboard_kpis.json — 10 templates, each naming a source cube,
a {{where}} placeholder, and an allowlist mapping generic filter names
(market, channel, device, platform, date_start, date_end) to actual
cube columns:
  dash_funnel_stages, dash_step_conversions, dash_completion_by_channel,
  dash_completion_by_device, dash_completion_channel_device,
  dash_downloads_by_channel, dash_pairing_by_channel,
  dash_pairing_by_platform_market, dash_d30_by_channel,
  dash_weekly_test_starts

Server-side WHERE composition (src/agent/dashboard.py:build_where) never
splices raw user text into SQL: a value is only ever included if (a) its
filter name is in that template's allowlist and (b) the value is present
in the cube's actual distinct values (cached), or is a validated
YYYY-MM-DD date; values are then quoted with embedded-quote doubling as
defense in depth. tests/test_dashboard.py::TestBuildWhereSafety
parametrizes several injection attempts (stray quotes, `; DROP TABLE`,
`OR 1=1`, comment sequences) and asserts each is rejected rather than
composed into the WHERE clause.

FILTERS MODEL
-------------
DashboardFilters (pydantic, extra="forbid"): date_start, date_end,
market, channel, device, platform — all optional.

- Relative ranges ("last 3 months", "son 3 ay") are resolved against
  MAX(event_timestamp) actually present in the data
  (agent.dashboard.get_data_horizon), never wall-clock "today" — this
  is a static demo dataset (June 2 - Aug 30 2026), so anchoring to
  today would silently return an empty dashboard once "today" runs
  past the data's own end.
- market/channel/device/platform are validated against real distinct
  values pulled from the cubes (cached per driver); an unrecognized
  value raises FilterValidationError naming the offending field, which
  every call site (API, agentic tool, FunnelAgent.ask) turns into an
  actionable 422 / tool-error / mode="error" response rather than a
  silent no-op filter or a crash.
- Natural-language extraction (agent.dashboard.extract_filters_from_text)
  is a separate, driver-less regex layer used by KeywordLLM.plan(), so
  the deterministic path doesn't need a driver just to parse text; date
  resolution happens one layer up, in FunnelAgent._ask_dashboard / the
  build_dashboard tool handler, both of which do have a driver.

DECISIONS / AMBIGUITIES
-------------------------
1. Added d30_eligible as a 4th measure on journey_weekly_cube beyond the
   literal 3 named in the brief, because d30_retained without a
   right-censoring-aware denominator cannot yield a correct rate.
2. Unified channel vocabulary across both cubes (mapped acquisition-
   channel buckets, not each source table's raw UTM/campaign string) so
   one `channel` filter value works identically against both cubes;
   documented that per-channel breakdowns from the cube therefore won't
   look byte-identical to gold.completion_by_channel's raw-campaign-
   keyed rows, even though SUM totals still match exactly.
3. journey_weekly_cube's d30 population is a documented dataset-specific
   exact match to gold.d30_by_channel's wider population, not a
   guaranteed structural equality — flagged explicitly in both the SQL
   COMMENT ON and the parity tests so a future dataset change doesn't
   silently look like a regression.
4. Split filter-text extraction (driver-less, regex-only) from relative-
   date resolution (driver-aware, anchored to MAX(event_timestamp)) into
   two layers, since KeywordLLM.plan() has no driver access but
   FunnelAgent.ask() and the build_dashboard tool handler both do.
5. Kept src/agent/dashboard.py free of any module-level import of
   agent.agent (self-contained narration/summary helpers instead) to
   avoid a circular import, since agent.agent needs agent.dashboard for
   _ask_dashboard.
6. Frontend filter-label text is generated server-side and is not
   independently translated for the TR UI (see screenshot note above) —
   judged acceptable since the surrounding chrome (chip title, clear
   button, aria-label) is fully localized and the label itself is a
   short, mixed English/date-and-code string ("Last 3 months · DE")
   either way.

ADDENDUM: IDEAL CHART FORMS (manager follow-up, same M11 module)
==================================================================

TRIGGER
-------
Dashboard charts almost always rendered as a plain vertical bar, because
every KPI's config declares one static `chart.type` and every card used
it verbatim. Follow-up request: compute the IDEAL chart form per result
and use it as the DEFAULT, while the existing manual per-card
chart-type switcher keeps working and a user's manual choice keeps
winning and persisting via the existing board-state localStorage.

Frontend-only change, as scoped: app/static/index.html. No backend
files touched, and no config/dashboard_kpis.json or src/agent/
metrics.yaml edits were needed either (see "No config changes needed"
below) — pytest stays at 377 passed, unchanged.

HEURISTIC (pickIdealChart(rows, spec), priority order)
--------------------------------------------------------
One pure function, applied wherever a card's chart is built from
{rows, chart spec}: legacy top-12 dashboard cards, the M11 filtered
~10-KPI dashboard cards, and an ad-hoc single-question chart card in
chat. Never mutates its inputs; returns {chart, rows} — a shallow
clone of the spec with `.type` possibly overridden, and either the same
rows reference or a freshly sorted copy.

1. Single row x single measure -> stat tile. (Already independently
   enforced by makeCard's own isStatShape() gate regardless of
   chart.type; pickIdealChart matches it too so its own contract stays
   honest, but this rule was never the gap being fixed.)
2. Temporal x (column name matching date/day/week/month/year/time, or
   an ISO-8601-looking value) -> line. Guarded off any hypothetical
   series-carrying result (none currently exist) so a future time+
   series KPI can't silently lose its breakdown to a single line.
3. Funnel / stage-ordered data -> keep the existing funnel/horizontal-
   bar treatment, rows left in the order the SQL already gave them —
   NEVER re-sorted by value. Detected generically off the app's own
   "stage"/"step" x-column naming convention (funnel_overview's
   `stage`, step_conversion_rates'/dash_step_conversions' `step`,
   dash_funnel_stages' `stage`) or an already-declared chart.type
   "funnel", rather than hardcoding metric keys — a future stage-
   ordered KPI keeps working without a JS change as long as it follows
   the same x-column naming.
4. Cross-tab with a series dimension -> grouped bar (existing rendering
   unchanged); DESIGN.md §2's legend rule (>=2 series -> legend on)
   already keys off series count at render time, so it needed no
   change.
5. Plain categorical -> sorted once, descending by value. Horizontal
   bar (new "hbar" chart type) when there are more than 6 categories OR
   any x-label is longer than 10 characters (the mapped channel-name
   vocabulary — "paid_social_tiktok" etc. — always trips this even at
   5 categories); vertical bar otherwise (e.g. device_category's short
   desktop/mobile/tablet labels). Sorting happens once in
   pickIdealChart, so the switcher's bar<->hbar toggle keeps showing
   the same meaningful order. Rate/percent axis formatting was already
   automatic (fmtValue already turns a 0..1 fractional value into a
   "%"-suffixed label wherever it's used as an axis formatter) — no
   change needed there.
6. Never pie/donut/dual-axis as a DEFAULT. Pie remains available as a
   manual-only choice via the existing switcher (unchanged), since nothing
   in the request asked to remove a working manual option — only to
   stop it (or a plain bar) from being the unconditional default.

DECISIONS / AMBIGUITIES (addendum)
-------------------------------------
1. Long-label threshold set at 10 characters and category-count
   threshold at the requested 6 — chosen so the mapped channel-name
   vocabulary (paid_social_meta, paid_search_brand, paid_social_tiktok,
   retargeting_meta, organic_direct — all 13+ characters) reliably
   trips the horizontal-bar branch even at only 5 categories, while
   short labels (device_category, market, platform) stay vertical.
2. Rule 3's stage/step detection is name-based ("stage"/"step" as the
   x column, or an already-declared chart.type "funnel") rather than a
   hardcoded list of metric keys, and also recognizes a companion
   "<x>_order" column as a secondary signal for any future KPI that
   uses different column naming — this was necessary because
   step_conversion_rates' underlying SQL (gold.step_conversion via
   metrics.yaml) does not select its own `stage_order` column into the
   output, so an order-column-only heuristic would have missed exactly
   the case named in the request ("step keys").
3. Deliberately left config/dashboard_kpis.json and src/agent/
   metrics.yaml untouched (see "WHAT CHANGED PER KPI" above) even
   though the request permitted refining them — the name-based
   detection in (2) already fixes the one static hint that mattered
   without touching a config value that backend narration logic also
   reads, keeping this a true frontend-only change with zero risk to
   the 377 passing backend tests.
4. A cross-tab (series) result is never forced into the temporal-line
   rule even though the priority list places rule 2 above rule 4 —
   added as a defensive guard (`!spec.series` before the temporal
   check) since buildEchartsOption's "line" case only ever plots one
   series and would otherwise silently drop a breakdown. No current
   KPI combines a temporal x with a series field, so this changes
   nothing observable today; it only prevents a latent bug for a
   future KPI that does.
5. Pie stays reachable only through the manual switcher, never as
   pickIdealChart's own pick (rule 6) — consistent with "the existing
   manual chart-type switcher... must keep working."


M11-FIX: DAILY GRAIN (approved by the user, real-run bug)
============================================================

ROOT CAUSE
----------
A real run of "Build me a KPI dashboard for the last 3 days for
Germany" silently produced a "last 6 weeks" dashboard instead. Two
causes, both required to fix:

1. The two M11 gold cubes were WEEK-grained (week_start). A day-level
   filter is structurally unanswerable off a week bucket — there is no
   query that turns "last 3 days" into a correct answer from data that
   is only ever cut by calendar week.
2. agent.dashboard._RELATIVE_RANGE_RE only recognized months/weeks
   (+ "ay"/"hafta"). Faced with "last 3 days", the real (tool-calling)
   LLM got back a ToolError from build_dashboard, and — rather than
   surfacing that mismatch to the user — quietly retried with a
   different, supported phrase ("last 6 weeks") and presented the
   result as if it were what was asked. The parser gap made the
   substitution possible; the missing "final answer must say what was
   actually applied" instruction is what let it go out silently.

RENAME MAP
----------
Every reference renamed together (grep-verified zero stale hits outside
intentional before/after history entries in docs/PROJECT_STATE.md):

  gold.web_funnel_weekly_cube  -> gold.web_funnel_daily_cube
  gold.journey_weekly_cube     -> gold.journey_daily_cube
  week_start (cube column)     -> day_date (cube column)

Touched: sql/medallion.sql (cube DDL + COMMENT ON, both now explaining
the day-grain choice and citing the M11-fix), src/agent/medallion.py
(GOLD_TABLES, still 14 gold objects), src/agent/dashboard.py (module
docstring, distinct-value queries, a code comment), src/agent/tools.py
(build_dashboard's tool description + relative_range example), app/
main.py (a code comment), config/dashboard_kpis.json (every template's

dash_weekly_test_starts keeps its title and line-chart behavior

BOUNDARY SEMANTICS (documented per the fix request)
-------------------------------------------------------
date_start = horizon - N <unit>, BOTH ENDS INCLUSIVE, for every unit
alike — this is the same convention weeks/months already used before
days existed ("last 1 week" already spans horizon-7..horizon inclusive,
8 days, not a clean 7), kept uniform rather than special-casing days.
Concretely: "last 3 days" against a horizon of 2026-08-30 spans
2026-08-27..2026-08-30 inclusive — 4 calendar days, not 3. This is a
deliberate choice, not an off-by-one bug: a caller wanting a strict
"N calendar days excluding today" window would pass N-1, which nothing
in this change requires.

HONESTY RULE
------------
- New agent.dashboard.UnparseableRangeError(ValueError): carries `phrase`
  and `supported_units` ("days", "weeks", "months"); its message names
  the supported units so an LLM can retry correctly.
- New agent.dashboard.resolve_relative_range(text, horizon): like
  parse_relative_range but RAISES UnparseableRangeError instead of
  returning None — used at call sites where the text arrives as an
  explicit "this names a range" argument (the build_dashboard tool),
  where silently doing nothing would repeat the exact bug this fix
  closes. agent.tools.ToolRegistry.build_dashboard now calls this and
  turns the structured error into a ToolError (so the agentic loop feeds
  it back to the LLM as a failed tool_result, same self-correction path
  every other tool failure already uses).
- agent.agentic.AgenticFunnelAgent's system prompt gained a HONESTY RULE
  sentence in the DASHBOARD INTENT paragraph: the model's final answer
  MUST state the exact applied filter_label verbatim, and say so
  explicitly (with why) whenever it differs from what the user actually
  asked — this is the half of the fix that closes the gap code alone
  cannot: even with days now parseable, a still-unsupported ask (e.g.
  "last 3 hours") or any other filter substitution must be disclosed,
  never silently presented as an exact match.
- Applied-range echo: run_dashboard()'s return gained `applied_range`
  ({"start", "end", "label"} or None) — the resolved date window in
  isolation from the compound filter_label string (which also bundles
  market/channel/device/platform). Threaded through agent.tools.
  build_dashboard (automatic, same dict), agent.agent._ask_dashboard,
  and both SSE dashboard-event emitters (agent.agentic + app.main's
  keyless fallback) and POST /api/ask's JSON response. POST /api/dashboard
  (structured filters, no natural-language parsing) does not carry it —
  a caller there always supplies already-resolved dates, so there is
  nothing to reconcile against a request phrase.

DECISIONS / AMBIGUITIES (this fix)
-------------------------------------
1. Boundary semantics for days deliberately mirror weeks/months' existing
   "-N units, both ends inclusive" convention rather than a "trailing N
   calendar days" convention, per the fix request's explicit instruction
   to keep it "consistent with existing week/month logic" — documented
   in parse_relative_range's docstring and in docs/api_contract.md.
2. "Add an applied-range echo" was implemented as a new `applied_range`
   field (isolated from filter_label) on run_dashboard's return, threaded
   through every natural-language surface (agentic + keyless SSE events,
   POST /api/ask's JSON) but NOT POST /api/dashboard's structured-filters
   response — that endpoint takes already-resolved dates and never parses
   a range phrase, so there is nothing for it to reconcile against a
   request.
3. docs/PROJECT_STATE.md's original M11 log entry was left untouched
   (matches this project's own convention of additive history) and a new
   "M11-fix tamamlandı" section appended after it, rather than rewriting
   history to pretend the cubes were always daily.
4. FunnelAgent._ask_dashboard (the deterministic KeywordLLM path) keeps
   calling parse_relative_range rather than resolve_relative_range: by
   construction, extract_filters_from_text only ever sets
   relative_range_text when the shared regex already matched, so
   parse_relative_range can never return None there — resolve_
   relative_range's structured error is specifically for the
   agentic-tool call site, where an LLM supplies relative_range as an
   independent, unverified argument.


===============================================================================
M11 ADDENDUM 2: SQL VISIBILITY ON DASHBOARD CARDS AND THE TRACE
===============================================================================

PROBLEM
-------
When a dashboard was built — the top-12 button or a natural-language
build_dashboard call — the SQL behind each KPI and its result rows were
not visible anywhere. Chat answers already had "Show SQL"/"Show data" via
addAgentMessage(); dashboard cards had neither, and the agent trace's
build_dashboard step was a dead end (no way to see what actually ran).

FIX — BACKEND (reuses the existing sqlfmt choke point, does not duplicate it)
------------------------------------------------------------------------
1. src/agent/dashboard.py: run_dashboard() now adds "sql" to every card,
   via `format_sql_for_display(sql)` — `sql` here is the KPI template
   with THIS request's WHERE already composed in (build_where(...)), the
   exact statement executed by driver.query(sql). The raw `sql` variable
   passed to the driver is untouched; only a formatted copy goes on the
   card, per sqlfmt.py's own documented contract. Both callers of
   run_dashboard — the filtered POST /api/dashboard branch and the
   build_dashboard agentic/keyless tool — inherit this for free (dash.py
   is the single place cards are built for the cube-backed path).
2. app/main.py: the legacy top-12 /api/dashboard branch adds
   `"sql": result.get("sql")` to each card — `result` is
   `agent.run_metric(key)`'s output, which already carries a formatted
   "sql" via FunnelAgent._payload() (the pre-existing M6 choke point), so
   no new formatting call was needed there at all.
3. src/agent/agentic.py: the "dashboard" SSE event gains a `"call_id"`
   field (the same id as the build_dashboard tool_call/tool_result pair)
   so the frontend can attach the per-KPI SQL list onto that exact,
   already-rendered trace step rather than guessing which step it belongs
   to. The keyless deterministic path (FunnelAgent._ask_dashboard) never
   goes through the tool-call loop, so its "dashboard" event has no
   call_id — the frontend treats that as "create a new trace step
   instead of attaching to one" (see below), not as an error case.

FIX — FRONTEND (app/static/index.html)
------------------------------------------------------------------------
1. makeCard()'s existing collapsible "Details" area (`.card-notes`) now
   also renders a "Show SQL" toggle (cardData.sql, via the existing
   highlightSql()) and a "Show data" toggle (rows, via the existing
   buildRowsTableHtml()) — the identical toggle pattern addAgentMessage()
   already uses for chat answers, just re-attached to dashboard cards.
   The Details area's visibility condition was widened from
   `answer || consent_note` to also include `sql` or a non-empty `rows`.
   renderDashboardGrid() (used by both the top-12 button and the filtered
   "dashboard" SSE event, via renderFilteredDashboard()) now threads
   `sql: c.sql` into each card's data — one code path covers both
   surfaces, as it already did for chart/rows/answer.
2. Trace: addStep()'s single-`opts.sql` rendering was factored out into a
   shared `appendSqlDisclosure(body, sql, sqlList)` helper that also
   supports a NEW `opts.sqlList` — an array of {title, sql} pairs,
   rendered as one toggle opening a titled list of SQL blocks (one per
   KPI). A new `trace.attachSqlList(callId, sqlList)` method looks up an
   already-rendered step by its `data-call-id` (the same lookup markDone()
   uses) and appends the disclosure post-hoc, since the build_dashboard
   tool_call step is created before any SQL exists and the SQL only
   arrives later in the "dashboard" event. In streamAsk()'s handling of
   that event: when `event.call_id` is present (agentic path), the list
   is attached onto the existing build_dashboard step; when absent
   (keyless path, no tool-call loop), a brand-new step is created directly
   from the event via `trace.addStep({..., sqlList})` — screenshotted
   below, since this session runs keyless.
3. CSS: `.trace-sql-list` / `.trace-sql-item` / `.trace-sql-item-title`
   added (existing tokens only, no new hues per DESIGN.md), plus
   `.trace-step .trace-sql-list pre.sql{display:block;}` — a higher-
   specificity override of the pre-existing `.trace-step pre.sql{display:
   none;}` rule, so a nested pre.sql inside the new list container isn't
   blanket-hidden by the older single-SQL rule. No `!important` used, per
   the codebase's established pattern (see the M9/M10 `[hidden]` fixes).
   No new i18n strings needed — showSql/hideSql/showData/hideData/
   cardNotesToggle were already translated (EN+TR) for the chat bubble.
