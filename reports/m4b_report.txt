M4b Test Report — Data Realism Fix: Multi-Touch Journeys + Repeat Test Starts
================================================================================
Date: 2026-09-02
Scope: src/generate_data.py (generator only), tests/test_medallion.py
       (one oracle SQL fix + 4 new planted-pattern tests), data/*.parquet
       (regenerated), docs/demo_qa_log.md (QA-2 marked done).
Untouched (per module boundary): sql/medallion.sql, metrics.yaml, app/,
       scripts/, docs/knowledge/attribution.md (already accurate, see below).


1. THE PROBLEM
----------------
Every synthetic user carried exactly ONE channel end-to-end: the utm that
started their web session was, by construction, also the utm on their
completion session. Because of that, gold.attribution_first_vs_last's
first-touch and last-touch models produced IDENTICAL per-channel numbers —
the flagship "do these two attribution models tell different stories?" KPI
had nothing to say. Separately, no user ever restarted the hearing test
(exactly one hearing_test_start per user), so "how many users started the
test more than once?" always had a trivial, uninteresting answer of zero
(see docs/demo_qa_log.md, QA-2 / scenario S3).


2. WHAT CHANGED IN THE GENERATOR
-----------------------------------
a) Multi-touch "switcher" journeys (src/generate_data.py, ~line 120-165):
   - Among DOWNLOADED users, ~25% become switchers: their completion
     session (hearing_test_complete, result_screen_view, app_store_redirect
     — the s2 events) now carries a utm DIFFERENT from the one that started
     them. Switch propensity is weighted 1.0 for the two discovery channels
     (paid_social_meta, paid_social_tiktok) vs. 0.18 for everything else,
     then calibrated (reusing the existing `calibrate()` helper) to a 25%
     mean among downloaders.
   - Among completed-but-NOT-downloaded users, the same weighting is
     calibrated to a 5% mean (the "optional, lower rate" case from the
     brief) — realistic: a user can multi-touch on the way to completing
     the test even without ever reaching the app.
   - Closing utm for switchers is drawn retargeting_meta 0.40 /
     brand_search 0.25 / organic-NULL 0.35 — "closing channels harvest
     what discovery channels created."
   - id_bridge.acquisition_channel is built from `channels`/`link["channel"]`
     directly and was NEVER touched by this change — it stays true
     first-touch, by construction, not by convention.
   - Ground truth gains 3 columns: `switcher` (bool), `closing_utm_final`
     (the utm actually used on the completion/repeat sessions), and
     `last_channel` (the closing utm mapped back to the channel vocabulary
     — same mapping id_bridge.acquisition_channel uses).

b) Repeat test starts (src/generate_data.py, ~line 166-180):
   - ~8% of ALL users (not just downloaders) emit 1-2 EXTRA
     hearing_test_start events in a later session (suffix s3, and s4 for
     the ~30% of repeaters who get a second one), 1-14 days after their
     first start, on the SAME pseudo_id (pseudo1) they started with.
   - utm on these extra events = closing_utm_final — i.e. whatever channel
     already closed the journey (or the original channel, for
     non-switchers) — deliberately, so the chronologically-latest event
     never silently redefines last-touch away from what the completion
     session already established.
   - Ground truth gains `repeat_start` (bool: this user has >=1 extra
     start).

c) `web()` helper generalized to take a `utm_col` parameter (was hardcoded
   to the single `utm` column) so start-session events keep the original
   utm while completion/repeat-session events can carry `closing_utm_final`.

d) New validation-report sections printed by the generator itself (see
   §4 and §6 below): a funnel invariant check recomputed from event-level
   data (with hard `assert`s, not just prints), switcher stats, and
   repeat-start stats.

No change to: RNG seed (still `np.random.default_rng(42)`), the funnel
probability model (p_complete/p_dl/p_pair/p_d30), censoring logic, output
schema of web_events/app_events/id_bridge (only _ground_truth.parquet, an
internal validation-only file, gained columns), or any planted-pattern
calibration constant.

One test-suite fix required by this change (tests/test_medallion.py):
_OLD_COMPLETION_BY_CHANNEL_SQL, an independent "pre-M3c" oracle used to
verify gold.completion_by_channel, picked a user's channel via
`COALESCE(MAX(utm_campaign), 'organic/none')`. That was only ever
equivalent to "last touch" because, pre-M4b, every user had exactly one
utm value ever. With real multi-touch data, MAX() of the utm STRING can
pick the alphabetically larger of two genuinely different values instead
of the chronologically later one (e.g. "summer_hearing_meta" > "retargeting_meta"
alphabetically even when retargeting_meta is the later, true last touch),
so the oracle silently stopped answering the question it was written to
answer. Fixed by re-deriving "last touch" the same way silver.web_user_stages
does — ROW_NUMBER() by event_timestamp DESC — but written independently,
straight off bronze/raw web_events, never touching silver/gold, preserving
the test's role as an independent check. This is the only SQL edit in this
module; every other oracle (funnel_overview, pairing_by_platform_market,
d30_by_channel) doesn't depend on utm_campaign and needed no change. Full
rationale is documented inline in test_medallion.py's module docstring.


3. FUNNEL INVARIANT — BEFORE / AFTER
----------------------------------------
Recomputed directly from gold.funnel_overview on the regenerated DuckDB
lakehouse, and cross-checked against event-level recomputation (§4 below)
and the generator's own ground-truth flags. All counts are UNCHANGED:

  stage                    before M4b   after M4b   match
  hearing_test_start          100,000     100,000    yes
  hearing_test_complete        42,062      42,062    yes
  app_download                 23,405      23,405    yes
  hearing_aid_paired           14,599      14,599    yes
  active_d30                    7,461       7,461    yes

Why this holds by construction: every switcher-relabeled or repeat-start
event added by M4b is an EXTRA row on a user who was already counted for
that stage before the change (funnel logic is MIN(event_timestamp) /
first-qualifying-event per user_pseudo_id, per silver.web_user_stages and
silver.app_user_stages) — never a new user, never a changed boolean flag.
Concretely: the switcher/repeat-start code runs strictly AFTER
completed/downloaded/paired/d30 (and their timestamps) are drawn from the
RNG stream in src/generate_data.py, so it cannot perturb those booleans
even indirectly through RNG-stream-position shifts.

8. PLANTED PATTERNS — SURVIVAL CHECK
-----------------------------------------
completion_by_channel is last-touch-grouped, so switchers legitimately
SHIFT its exact rates (this is the realistic "last touch flatters closers"
effect the brief calls out, not a bug):

  channel               test_starts  test_completes  completion_rate
  retargeting_meta             9948            5257           0.528
  brand_search                11103            5744           0.517
  organic/none                32927           16875           0.512
  summer_hearing_meta         29409            5284           0.180
  tiktok_awareness            16613            2531           0.152

organic > tiktok still holds, and by a WIDER margin than before (0.512 vs
0.152, ~3.4x) — realistic, because switchers pull discovery-channel
closers OUT of tiktok's last-touch bucket, lowering it further. The
generator's own channel-level (first-touch, unaffected by switching)
completion print is unchanged in structure:

  channel               completed rate (first-touch grain)
  organic_direct         0.587
  paid_search_brand      0.540
  retargeting_meta       0.482
  paid_social_meta       0.295
  paid_social_tiktok     0.258

All 5 required invariants hold, verified both in the generator's own
validation print and now as pytest assertions
(tests/test_medallion.py::TestPlantedPatternsSurviveM4b, 4 new tests):

  1. organic completion >> tiktok completion            -- holds (~3.4x on
     the last-touch gold mart; asserted at a >1.5x floor for headroom)
  2. desktop >> mobile completion                        -- holds (pre-
     existing test, unaffected by M4b, still green)
  3. iOS pairing ~+9pt within market                     -- holds. On the
     raw downloader population (generator's own ground-truth print, the
     level the +9pt figure was originally calibrated at): DE 0.570/0.680
     (+11.0pt), UK 0.584/0.669 (+8.5pt), US 0.584/0.669 (+8.5pt). On
     gold.pairing_by_platform_market (bridge-linked subset only, smaller
     N, some sampling noise expected): DE 0.579/0.649 (+7.0pt), UK
     0.602/0.663 (+6.1pt), US 0.585/0.672 (+8.7pt). Either way iOS > Android
     in every market — platform/market/paired are fixed before M4b's new
     RNG draws run, so this pattern is structurally untouched by M4b.
  4. tiktok low pairing                                  -- holds (tiktok's
     pairing_rate, 0.4097, is the minimum of all 5 channels on
     gold.pairing_by_channel — first-touch grain, unaffected by switching)
  5. linkable share DE < UK < US                         -- holds (0.213 <
     0.290 < 0.385 on gold.linkable_share_by_market)

No threshold on any PRE-EXISTING test needed to be tweaked. The only test
change beyond the 4 new assertions above is the oracle-SQL fix in §2.
