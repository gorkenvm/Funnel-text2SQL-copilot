NEW BACKEND SURFACE
--------------------
GET /api/catalog — app/main.py
  - Returns {"layers": {"bronze": [...], "silver": [...], "gold": [...]}},
    built directly from agent.medallion.BRONZE_TABLES / SILVER_TABLES /
    GOLD_TABLES (imported, not re-derived) so it can never drift from the
    agent's own table whitelist.
  - Each entry is {"name": "<layer>.<object>"} plus an optional "comment"
    (the object's COMMENT ON text) when cheaply available.
  - Comments are fetched with exactly two whole-catalog queries total
    (duckdb_tables()/duckdb_views(), both scoped to bronze/silver/gold) —
    never one query per object, per the spec's "skip if it needs extra
    queries per object" rule. Both queries are wrapped in try/except so a
    Databricks-backed deployment (no such introspection functions) simply
    ships without comments instead of 500ing.
  - Row counts intentionally omitted (same reasoning).
  - Reuses _json_safe() for the response, per the task's backend-change
    constraint.
  - Documented in docs/api_contract.md under "GET /api/catalog (M8)".
  - Tested in tests/test_api.py::test_catalog_lists_medallion_layers —
    checks all three layers present, gold has >= 12 entries, every name is
    qualified with its own layer prefix, and any comment present is a
    non-empty string.

DEVIATIONS / NOTES
-------------------
1. Stat-card verification used an extracted-and-hooked copy of the app's
   own JS (see m8_stat_tile_fixture.png above) rather than the live app,
   because none of the 12 registered gold KPIs — nor the keyless demo's
   registry-only ask() path — ever produces a genuine single-row result
   to trigger the "Kart" view naturally. The stat-tile code path itself
   is unmodified production code; only the verification harness is
   synthetic. This mirrors the task's own "if reproducible" hedge for
   screenshot (c).
2. The data catalog panel was implemented as a fixed-position, backdrop-
   dismissible drawer toggled from a header button ("📚 Catalog"), sliding
   in from the left edge of the whole page rather than being permanently
   docked inside the dashboard column — chosen specifically so it never
   resizes/steals space from the chat panel on mobile (verified above),
   per the task's explicit constraint.
3. Per-card dashboard latency is measured as elapsed time from the
   /api/dashboard request start to the moment each card is constructed
   in the render loop (not a separate timing per metric on the backend,
   since all 12 metrics return in a single response) — cards later in the
   grid show a marginally larger elapsed time, which is an accurate
   (if small) reflection of sequential client-side render cost.
4. All six features' new user-facing strings are present in both the EN
   and TR i18n dictionaries (I18N.en / I18N.tr) in app/static/index.html.
5. No changes were made under src/agent/ — the catalog endpoint only
   imports the existing BRONZE_TABLES/SILVER_TABLES/GOLD_TABLES tuples
   from agent.medallion, per the task's backend-change constraint.
6. Every new localStorage access (funnelCopilotBoard_v1 read/write) is
   wrapped in try/catch, matching the existing funnelCopilotChips_v1 /
   funnelCopilotTier_v1 convention; corrupt/unexpected shapes fall back to
   defaults exactly like the existing chip-state loader.
