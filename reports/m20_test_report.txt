M20 — Full de-branding sweep to the new "Funnel Copilot" identity
====================================================================

Trigger
-------

hearing-aid brand name publicly is unwise. New identity, on purpose

subtitle/scenario wording "hearing-care funnel demo" / "synthetic

undo its own sweep. The two files that legitimately still need to spell
out an old literal value — so an existing user can find and act on it —
are named below under "Deliberate exceptions", with the reasoning.

Deliberate exceptions (8 remaining hits — flagged, not missed)
-----------------------------------------------------------------
Two files still spell out an old literal value, on purpose, inside a
migration note aimed at an existing user — this is in direct, acknowledged
tension with the "final grep must return zero hits" acceptance line, and I
resolved it in favor of the note being actually useful: silently hiding
the old value would make the note useless (a user would not know what
string to look for in their own environment/override file).

  - docs/deploy_guide.md (4 hits): the DATABRICKS_SCHEMA migration note
    names the old schema default explicitly, and gives the exact env-var
    line an existing user would add to their private .env to keep reading
    their existing data — exactly what the coordinator's own instructions
    asked this note to say.
  - docs/deploy_runbook_vps.md (4 hits): the new VPS migration callout
    (added per the coordinator's explicit ask for a container-name
    migration note) names the old hostname and old example container name
    so a reader can find and update their own compose override and
    Cloudflare route.

Recommend the coordinator/user decide whether these 8 historical-value
mentions inside migration notes are an acceptable permanent, narrow
exception (my recommendation) or whether the exact old values should
instead live only in a private/internal note. I did not unilaterally
choose the latter since it would make the guides materially less useful
to the one audience — an existing deployer — who actually needs them.

Migration notes (for the user)
-------------------------------
1. VPS deploy (hostname + container name): if the app is currently live
   under the old brand-named subdomain, per deploy_runbook_vps.md's new
   M20 callout:
     a. `docker compose down`
     b. if your compose override sets an explicit old-named
        `container_name`, change it to `funnel_copilot` (this repo's own
        docker-compose.yml already uses the service name "funnel-copilot",
        unaffected)
     c. `docker compose up -d`
     d. update the Cloudflare Tunnel route: hostname -> funnel.vmgorken.com,
        and (container-mode tunnels only) the Public Hostname target URL ->
        http://funnel_copilot:8000; remove the old route from the
        Cloudflare panel once the new one is confirmed working.
2. Databricks schema (default renamed to "funnel"): if you have EXISTING
   data loaded under the old default schema name, the code change does not
   move it. Two options (documented in deploy_guide.md):
     a. Keep using your existing data: add the old schema name explicitly
        as `DATABRICKS_SCHEMA=...` to your private .env (the env-override
        path still works, unchanged) — see deploy_guide.md's migration
        note for the exact value, OR
     b. Move to the new default: re-run `scripts/load_to_databricks.py` to
        load into the new "funnel" schema.
   Installs on the default `AGENT_DB=duckdb` driver are unaffected.
