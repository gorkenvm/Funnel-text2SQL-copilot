4. DIALECT RISKS NOT VERIFIABLE IN THIS SANDBOX
--------------------------------------------------
This environment has no network access to a Databricks workspace, so
sql/medallion.sql has been executed and equivalence-tested against DuckDB
only. The following statements/constructs are believed portable (several
were already relied upon, unmodified, by the pre-M3c metrics.yaml) but
have NOT been run against a real Databricks SQL warehouse:

  a. `timestamp_expr + INTERVAL 28 DAY` / `- INTERVAL 34 DAY` (used in
     silver.app_user_stages' d30_hits/censored logic). DuckDB accepts the
     singular unit form; Databricks/Spark SQL is documented to accept it
     too, but this has not been executed there.
  b. `DATE_TRUNC('week', ts)` (gold.weekly_test_starts). Both engines
     support DATE_TRUNC with a 'week' unit, but week-start-day conventions
     (Monday vs. Sunday) have not been cross-checked against a live
     Databricks warehouse — if they differ, weekly_test_starts' week_start
     values (not row counts) could shift by a few days.
  c. `COMMENT ON TABLE ... IS '...'` / `COMMENT ON VIEW ... IS '...'` for
     all 17 objects. Verified to work on DuckDB 1.5.5. Databricks SQL
     documents COMMENT ON support but this was never executed against a
     live workspace — if a permission or version issue rejects one,
     agent.medallion.apply_medallion logs it and continues (verified by
     tests/test_medallion.py::TestApplyMedallion::
     test_comment_on_failure_is_logged_and_non_fatal), so a rejection
     would not block the layers themselves, only lose that one comment.
  d. `CREATE SCHEMA IF NOT EXISTS <bare_name>` resolving under the
     connection's default catalog (so bronze/silver/gold land in the same
     catalog scripts/load_to_databricks.py loaded the raw tables into).
     This is standard Unity Catalog behaviour but was not exercised
     end-to-end here.
  e. Window function `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...
     DESC)` and `LAG(...) OVER (ORDER BY ...)` — standard ANSI window
     functions, expected to be identical on both engines, not run on
     Databricks here.
  f. `1.0 * a / NULLIF(b, 0)` division-by-zero guarding and `||` string
     concatenation (gold.step_conversion's `step` column) — both DuckDB
     and Spark SQL support `||`, but again unverified live.

None of these risks are new: (a), (b) and (f) already existed, unchanged,
in the pre-M3c metrics.yaml and were presumably already accepted as
portable by the M3b author. (c), (d) and (e) are the genuinely new
surface area this module adds.


5. DEVIATIONS FROM THE TASK'S LITERAL WORDING
------------------------------------------------
- The D30 window is implemented as the ORIGINAL metrics.yaml semantics —
  event_timestamp >= first_open_ts + INTERVAL 28 DAY AND
  event_timestamp <  first_open_ts + INTERVAL 35 DAY (28-34 days
  inclusive) — rather than the task prompt's shorthand
  "[first_open+28d, first_open+34d)". The RULES explicitly require KPI
  values to remain identical to before, and metrics.yaml's own header
  comment already documented the 28-34-inclusive/right-censoring
  semantics this preserves; changing the boundary would have silently
  changed every D30-based KPI's numbers.
- silver.web_user_stages.market is sourced from bronze.web_events.country
  (renamed), not a new field — verified empirically that every bridge
  row's web_pseudo_id has a country that always equals that bridge row's
  own `market` value (0 mismatches across 6,863 bridge rows), and that
  country/device_category/consent_state/utm_campaign are all stable
  (single-valued) per user_pseudo_id in this dataset (0 counter-examples),
  which is what makes a clean user-grain silver table possible at all.
- gold.pairing_by_platform_market and gold.d30_by_channel are deliberately
  built from silver.app_user_stages JOIN silver.v_attribution_eligible
  directly (NOT from silver.linked_journeys) — the original KPI SQL for
  both never required first_open_ts > test_complete_ts, and routing them
  through linked_journeys would have changed their populations. This is
  called out explicitly in each mart's COMMENT ON.
- ~6% of web_user_stages users (6,371 of 106,371) have a
  first_test_complete_ts with no first_test_start_ts — a data-quality
  artifact of the generator (unrelated to this task; data/ and
  generate_data.py were not touched). gold.completion_by_channel and
  gold.completion_by_device reproduce the original's
  `WHERE first_test_start_ts IS NOT NULL` filter exactly, so this noise
  is excluded identically to the pre-M3c behaviour (verified by the
  KPI-equivalence tests, not by inspection alone).
