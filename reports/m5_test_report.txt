5. BAND MATH — hand-computed boundary checks (TestBandMath)
-------------------------------------------------------------
sentinel_core._band_severity(deviation_z, volume_signal, history_days,
thresholds) is exercised directly, with hand-picked inputs, independent of
any driver or real data:
  - exact boundaries: |z|=1.5 -> info, |z|=2.5 -> warning, |z|=4.0 ->
    critical (both signs)
  - |z|=1.49 -> no finding (just under the info floor)
  - z=None / z=NaN -> no finding (undefined band, e.g. zero spread)
  - volume_signal one below min_volume_floor -> suppressed even at z=10;
    at the floor -> not suppressed (alert-fatigue guard, PDF requirement)
  - history_days one below min_history_days -> suppressed even at z=10;
    at the minimum -> not suppressed
evaluate_volume_findings() is also exercised on a 2-row hand-built
DataFrame (a manufactured -6.0σ series and a +0.1σ series) and correctly
returns exactly one Finding, for the -6.0σ row, severity critical.

6. DESIGN DECISION WORTH FLAGGING: default as-of is NOT the literal max
   event date
------------------------------------------------------------------------
The PDF/spec phrasing was "as-of = max date" for the healthy-run
acceptance test. Empirically, this dataset's literal maximum event date
(2026-08-30) is a partial/immature day by construction of the closed,
finite generator window (the very last calendar day; several downstream
event types such as app_open and app_store_redirect are also naturally
lagged behind an earlier step in the same journey, and progressively
under-observed in the ~6 days closest to the horizon) — scoring it
directly manufactures large, spurious deviations across nearly every
series (deviation_z as extreme as -23 on a perfectly healthy dataset).

This mirrors a pattern the codebase already has:
silver.app_user_stages.censored (sql/medallion.sql) right-censors D30
retention near the data horizon for the same underlying reason. Sentinel
applies the same idea at the day-volume level:
agent.sentinel_core.default_as_of() returns MAX(event_date) minus
EVENT_MATURITY_BUFFER_DAYS (6, chosen empirically — see the constant's
docstring for the measurements), and this buffered date is what "the
sentinel's default as-of" means throughout this deliverable, including
the healthy-run acceptance test.

This was not silently smoothed over: tests/test_sentinel.py has
TestHealthyRun::test_scoring_the_raw_max_event_date_is_intentionally_unsafe,
which deliberately scores the literal raw max date and asserts it DOES
trip a critical finding — proving the buffer is an examined, deliberate
choice, not a threshold tuned to hide a bug. `--as-of` always lets a human
override the default and score any day, including an immature one.

7. OTHER DEVIATIONS / NOTES
----------------------------
- Registry (config/sentinel_registry.json) was generated once from the
  current DuckDB data via agent.sentinel_core.build_registry() — not
  hand-typed. Its "thresholds" block (band multipliers, min_volume_floor,
  min_history_days) are the one part of the registry that IS a judgment
  call rather than derived from data; documented and justified in
  docs/sentinel_design.md's "False-positive management" section.
- daily_event_volumes.sql's "segment" column is market (web_events.country)
  for web-sourced rows and platform (app_events.platform) for app-sourced
  rows, because app_events carries no market/geo field at the event grain
  — documented in the SQL file's header rather than silently conflating
  the two meanings.
- daily_funnel_rates.sql's three step rates are same-day ACTIVITY ratios
  (today's "to" count over today's "from" count), not the cohort/
  first-occurrence conversion rate gold.step_conversion computes — a fast,
  cheap day-over-day drift signal, explicitly not a KPI of record.
  Documented in the file's own header, same spirit as sql/medallion.sql's
  mart-level caveats.
- notebooks/sentinel_job.ipynb tries a real `from agent import
  sentinel_core as sc` first (works when the repo is checked out as a
  Databricks Repo, the normal case for a Job notebook task living in this
  repo) and falls back to a mirrored subset of the same module, clearly
  labeled, if that import fails. BOTH paths were executed and verified
  outside Databricks in this sandbox (dbutils/spark faked over the same
  local DuckDB data) and produced byte-identical findings to
  scripts/sentinel.py's own run — see WHAT CANNOT BE VERIFIED below for
  what this substitute cannot prove.

8. WHAT CAN ONLY BE VERIFIED ON THE USER'S DATABRICKS
--------------------------------------------------------
This sandbox has no Databricks network access (same constraint every
prior module's report has noted for sql/medallion.sql). sql/sentinel/*.sql
mirrors medallion.sql's already-adopted, Databricks-safe construct set
(AVG/STDDEV window functions with an explicit frame, named WINDOW clauses,
FULL OUTER JOIN, information_schema.columns, current_catalog()/
current_schema()) but has been exercised here only against DuckDB. Once
the loader/notebook are run for real:
  - Confirm the three sql/sentinel/*.sql queries execute unmodified via
    spark.sql() against the Unity Catalog tables scripts/load_to_databricks.py
    created (this is the one genuinely untested dialect risk — window
    frames and named WINDOW clauses are standard ANSI SQL Spark supports,
    but only a real run proves it end to end on this warehouse).
  - Regenerate config/sentinel_registry.json from the Databricks
    connection (agent.sentinel_core.build_registry(get_driver("databricks")))
    and expect exactly one, harmless "type changed" WARNING the first time
    (event_timestamp/linked_at: DuckDB reports TIMESTAMP_NS, Databricks
    reports TIMESTAMP) — documented in docs/sentinel_design.md's last
    section so it isn't mistaken for a real drift the first time it's seen.
  - Confirm notebooks/sentinel_job.ipynb's real import path actually
    activates (i.e. the repo is genuinely checked out as a Databricks Repo
    at the path the `repo_root` widget expects) rather than silently
    falling into its mirrored fallback cell every run.
  - Confirm the /Volumes/<catalog>/<schema>/raw/sentinel/ write succeeds
    with the Job's actual identity/permissions (docs/deploy_guide.md §7.4
    lists the exact grants needed).
  - Create the actual Databricks Workflows Job (Workflows → Create Job →
    notebook task → daily 06:00 schedule) — docs/deploy_guide.md §7 has the
